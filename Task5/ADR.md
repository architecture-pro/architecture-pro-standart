### <a name="_3bfxc9a45514"></a>**Функциональные требования**

**Use Cases**

**UC1**  
**Действующие лицо:** Новый клиент, сайт, Products Service, Application Service</br>
**Use Case:** Подача кредитной заявки на сайте</br>
**Описание:**

1. Клиент открывает сайт банка и просматривает доступные кредитные предложения
2. Выбирает кредитный продукт
3. Указывает ФИО и номер телефона
4. При желании предоставляет паспортные данные
5. Отправляет кредитную заявку
6. Application Service сохраняет заявку для дальнейшей обработки

**UC2**  
**Действующие лицо:** Новый клиент, Application Service, система скоринга, бюро кредитных историй</br>
**Use Case:** Получение предварительного решения по кредиту</br>
**Описание:**

1. Клиент предоставляет паспортные данные при оформлении заявки на сайте
2. Application Service обращается к существующей системе скоринга
3. Система скоринга использует доступные данные и сведения бюро кредитных историй
4. При наличии достаточных данных формируется предварительное решение
5. Клиент получает предварительное решение по кредиту

**UC3**  
**Действующие лицо:** Клиент, интернет-банк, Products Service, Application Service</br>
**Use Case:** Подача кредитной заявки в интернет-банке</br>
**Описание:**

1. Клиент авторизуется в интернет-банке
2. Просматривает доступные кредитные продукты и условия
3. При наличии видит предодобренное кредитное предложение
4. Выбирает предложение и указывает счёт зачисления средств
5. Заполняет необходимые данные и отправляет заявку
6. Подтверждает операцию СМС-кодом
7. Заявка передаётся на дальнейшую обработку

**UC4**  
**Действующие лицо:** Клиент, Application Service, система скоринга</br>
**Use Case:** Повторный скоринг при изменении обстоятельств клиента</br>
**Описание:**

1. Клиент подаёт заявку по предодобренному кредитному предложению
2. Если обстоятельства клиента изменились, инициируется повторный скоринг
3. Система скоринга выполняет проверку по упрощённой процедуре
4. Результат используется для дальнейшей обработки заявки

**UC5**  
**Действующие лицо:** Клиент, сотрудник отделения, АБС</br>
**Use Case:** Продолжение кредитной заявки в отделении</br>
**Описание:**

1. Клиент приходит в отделение банка
2. Сотрудник проверяет наличие ранее созданной онлайн-заявки
3. Если заявка существует, сотрудник продолжает работу с ней
4. Если клиент обращается впервые и заявки нет, сотрудник создаёт новую кредитную заявку в АБС

**UC6**  
**Действующие лицо:** Application Service, кредитный конвейер, сотрудник управления кредитования</br>
**Use Case:** Обработка кредитной заявки</br>
**Описание:**

1. Application Service передаёт кредитную заявку в кредитный конвейер
2. Заявка поступает на обработку без ожидания существующей суточной выгрузки из АБС
3. Сотрудник управления кредитования обрабатывает заявку в кредитном конвейере
4. Для заявок по предодобренным предложениям целевой срок обработки — тот же рабочий день
5. Результат обработки становится доступен для дальнейшего информирования клиента

**UC7**  
**Действующие лицо:** Клиент, Application Service, СМС-шлюз</br>
**Use Case:** Информирование клиента о кредитной заявке</br>
**Описание:**

1. Клиент отправляет кредитную заявку
2. Для нового клиента после подачи заявки инициируется СМС о необходимости посещения отделения для идентификации и получения кредита
3. При изменении статуса кредитной заявки инициируется СМС-уведомление
4. Существующий СМС-шлюз обеспечивает отправку сообщения клиенту

### <a name="_qmphm5d6rvi3"></a>**Решение**

[Диаграмма контейнеров C4](./с4/container/to-be/to-be-container.puml))
[Диаграмма контекста C4](./с4/context/to-be/to-be-context.puml))

**Логика архитектурных решений**

1. Используем существующий Application Service на Java / Spring Boot для приёма и обработки кредитных заявок
2. Используем Products Service для предоставления кредитных продуктов и условий сайту и интернет-банку
3. Сохраняем Applications DB на MS SQL для хранения заявок и статусов
4. Интернет-банк взаимодействует с Application Service через HTTPS / REST без прямого обращения к API АБС
5. Используем существующую систему скоринга Python / Flask, не создаём отдельный сервис кредитной оценки
6. При необходимости повторного скоринга используем упрощённую процедуру существующей системы скоринга
7. Кредитные заявки передаются из Application Service в существующий кредитный конвейер через REST API, как предусмотрено предыдущим архитектурным решением
8. Сохраняем существующую АБС для работы сотрудников отделений с кредитными заявками
9. Используем Kafka для асинхронной передачи заявок и событий, как предусмотрено архитектурой MVP
10. Для уведомлений используем существующий СМС-шлюз, не создаём дополнительный сервис уведомлений
11. Не изменяем существующий суточный обмен между АБС и кредитным конвейером. Для онлайн-заявок используем отдельный путь через Application Service

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. Доработка монолита интернет-банка для реализации кредитного процесса
1. Прямая интеграция интернет-банка с API АБС
1. Передача всех кредитных заявок через АБС с использованием существующей суточной выгрузки
1. Разработка отдельного сервиса кредитного скоринга
1. Создание отдельного Credit Application Service

**Недостатки, ограничения, риски**

1. Передача кредитных заявок и получение информации об их обработке могут увеличить нагрузку на перегруженную БД АБС
2. Суточная выгрузка из АБС в кредитный конвейер не подходит для оперативной обработки онлайн-заявок
3. Проверка кредитных заявок увеличивает количество обращений к системе скоринга
4. Статусы заявок в Application Service, АБС и кредитном конвейере могут различаться из-за задержек передачи данных
5. При сбоях и повторной доставке сообщений Kafka необходимо исключить создание дублирующих кредитных заявок
