### <a name="_3bfxc9a45514"></a>**Функциональные требования**

**Use Cases**

**UC1**  
**Действующие лицо:** Новый клиент, сайт </br>
**Use Case:** Подача заявки на депозит на сайте </br>
**Описание:**

1. Клиент открывает список доступных депозитов с актуальными ставками
2. Клиент выбирает депозит
3. Указывает ФИО и номер телефона
4. Отправляет заявку на депозит
5. Заявка становится доступна для дальнейшей обработки менеджером кол-центра

**UC2**  
**Действующие лицо:** Менеджер кол-центра, система кол-центра</br>
**Use Case:** Обработка заявки на депозит с сайта</br>
**Описание:**

1. Менеджер изучает поступившую заявку в системе кол-центра
2. Менеджер связывается с клиентом
3. При необходимости предлагает особые условия
4. Клиенту необходимо прийти в отделение для идентификации

**UC3**  
**Действующие лицо:** Клиент, интернет-банк</br>
**Use Case:** Подача заявки на депозит в интернет-банке</br>
**Описание:**

1. Клиент просматривает доступные депозиты, актуальные и персонализированные ставки
2. Выбирает депозит
3. Указывает счёт и сумму депозита
4. Отправляет заявку
5. Подтверждает операцию СМС-кодом
6. Заявка передаётся на обработку

**UC4**  
**Действующие лицо:** Менеджер бэк-офиса, АБС</br>
**Use Case:** Обработка заявки на депозит</br>
**Описание:**

1. Менеджер получает заявку на открытие депозита
2. Обрабатывает заявку в АБС
3. Подтверждает условия депозита
4. Клиент получает СМС после подтверждения размера ставки
5. После открытия депозита клиент получает СМС-уведомление

**UC5**  
**Действующие лицо:** Сотрудники бэк-офиса депозитов и кредитов</br>
**Use Case:** Работа с депозитными ставками</br>
**Описание:**

1. Сотрудник работает с актуальными депозитными ставками
2. Ставки доступны сотрудникам депозитного и кредитного бэк-офиса
3. Ставки используются при работе с депозитными заявками

**UC6**  
**Действующие лицо:** Новый клиент, сайт, система кредитного скоринга, бюро кредитных историй</br>
**Use Case:** Подача кредитной заявки на сайте</br>
**Описание:**

1. Клиент просматривает предложение по кредиту
2. Указывает ФИО и номер телефона
3. При указании паспортных данных может быть получено предварительное решение
4. Для принятия решения используются данные системы скоринга и общие данные бюро кредитных историй
5. При предоставлении паспортных данных клиент получает предварительное решение по кредиту
6. После подачи заявки клиент получает СМС о необходимости прийти в отделение для получения кредита и идентификации

**UC7**  
**Действующие лицо:** Сотрудник отделения, АБС</br>
**Use Case:** Работа с кредитной заявкой в отделении</br>
**Описание:**

1. Клиент приходит в отделение
2. Сотрудник проверяет наличие ранее созданной на сайте заявки
3. Если заявка существует, сотрудник продолжает работать с этой же заявкой
4. Для полностью нового клиента сотрудник создаёт новую кредитную заявку

**UC8**  
**Действующие лицо:** Клиент, интернет-банк</br>
**Use Case:** Подача кредитной заявки в интернет-банке</br>
**Описание:**

1. Клиент просматривает доступные кредиты и актуальные условия
2. При наличии видит предодобренное предложение
3. Указывает счёт зачисления средств и данные для подачи заявки
4. Отправляет кредитную заявку
5. Подтверждает операцию СМС-кодом

**UC9**  
**Действующие лицо:** Клиент, система кредитного скоринга</br>
**Use Case:** Повторный скоринг при подаче кредитной заявки</br>
**Описание:**

1. Клиент подаёт заявку по предодобренному предложению
2. Если ситуация клиента изменилась, выполняется повторный скоринг по упрощённой процедуре
3. Результат используется для дальнейшей обработки кредитной заявки

**UC10**  
**Действующие лицо:** Сотрудник управления кредитования, кредитный конвейер</br>
**Use Case:** Обработка кредитной заявки</br>
**Описание:**

1. Кредитная заявка поступает в Кредитный конвейер
2. Сотрудник обрабатывает заявку
3. Предполагается обработка заявок по предодобренным предложениям в течение того же рабочего дня

**UC11**  
**Действующие лицо:** Клиент, СМС-функционал</br>
**Use Case:** Информирование о статусе кредитной заявки</br>
**Описание:**

1. Статус кредитной заявки изменяется
2. Клиент получает СМС-уведомление об изменении статуса заявки

### <a name="_qmphm5d6rvi3"></a>**Решение**

[Диаграмма контейнеров C4](./с4/container/to-be/to-be-container.puml))
[Диаграмма контекста C4](./с4/context/to-be/to-be-context.puml))

**Логика архитектурных решений**

1. Избегаем масштабной переработки монолита и зависимости от подрядчика
2. Изолируем новые процессы оформления продуктов, выделить Application Service
3. В банке уже есть специалисты с опытом Java, используем Spring Boot
4. MS SQL - существующая технология банка
5. Используем Kafka для асинхронной передачи заявок и событий, чтобы снизить зависимость новых сервисов от доступности АБС
6. Сохраняем АБС, в MVP сотрудники продолжают обрабатывать депозитные заявки вручную
7. Используем существующий скоринг, не дублируем кредитную логику
8. Сохраняем действующий процесс обработки кредитных заявок
9. Использовать существующий СМС-шлюз, не создаём дополнительную систему уведомлений

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. Возможна доработка существующего монолита интернет-банка без выделения отдельных сервисов
2. Возможна прямая синхронная интеграция интернет-банка с API АБС
3. Возможно использование синхронных REST-интеграций вместо Kafka для всех взаимодействий

**Недостатки, ограничения, риски**

1. Kafka сама по себе не устраняет нагрузку на АБС. Потребуется отдельный механизм контролируемой обработки сообщений и интеграции с АБС
2. Интернет-банк несовместим с Kafka, поэтому взаимодействие интернет-банка с Application Service предлагается выполнять через REST API
3. Реализация СМС-подтверждений без изменения ядра интернет-банка может потребовать дополнительной интеграции с существующим СМС-функционалом
4. Отказоустойчивость между двумя ЦОД пока не раскрыта
5. Products Service должен получать актуальные ставки из определённого источника
6. Текущий интернет-банк работает на одной группе серверов в основном ЦОД, для выполнения требований доступности 99,9% необходимо реализовать отказоустойчивость с использованием резервного ЦОД
